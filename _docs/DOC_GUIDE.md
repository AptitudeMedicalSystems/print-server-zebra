# 文档规范 (Documentation Guide)

本项目采用统一的四类文档体系，适用于项目级 `_docs/` 和每个服务的 `_docs/`。

## 目录结构

```
_docs/
├── architecture/    # 活文档，反映当前系统状态
├── design/          # 版本化设计文档
├── plan/            # 实施计划
└── execution/       # 实施记录
```

---

## 1. `architecture/` — 系统现状 ("现在是什么样")

> 活文档，始终反映当前架构，有变更就更新。

**核心文件:** `overview.md`

| Section | 内容 | 用途 |
|---------|------|------|
| System Overview | 一句话说明服务职责 | "这个服务是干什么的" |
| Component Diagram | 内部模块关系图 (text/mermaid) | "有哪些模块，怎么连接" |
| Data Flow | 数据从哪来、到哪去、格式是什么 | "数据流怎么走" |
| Interfaces | 暴露的 API / Redis channels / MongoDB collections | "跟其他服务怎么通信" |
| Tech Stack | 依赖的框架、库、版本 | "用了什么技术" |
| Deployment | 运行方式、端口、环境变量 | "怎么部署/启动" |

**更新时机:** 每次影响架构的代码变更后。

---

## 2. `design/` — 设计决策 ("为什么这样做")

> 每个重要设计一个文件，可以有修订版。

**命名:** `<feature>.md` 或 `<feature>_rev<N>.md`

| Section | 内容 | 用途 |
|---------|------|------|
| Motivation | 为什么需要这个设计/变更 | "解决什么问题" |
| Proposed Solution | 方案描述、数据模型、流程 | "具体怎么做" |
| Alternatives | 考虑过的其他方案及放弃原因 | "为什么不选别的方案" |
| Impact | 影响的服务/模块/数据 | "改了什么范围" |
| Revision History | 修订记录 (日期, 原因, 变更) | "设计演进过程" |

**更新时机:** 有重要设计决策或架构变更时。

---

## 3. `plan/` — 实施计划 ("打算怎么做 → 实际做了什么")

> 执行前写计划，执行后写回结果。

**命名:** `<feature>_plan.md`

| Section | 内容 | 用途 |
|---------|------|------|
| Objective | 目标和范围 | "要完成什么" |
| Tasks | 任务分解 (phases/steps) | "分几步做" |
| Dependencies | 前置条件、依赖服务 | "需要先准备什么" |
| Status | 每个 task 的状态标记 | "做到哪了" |
| **[Post]** Results | 实际结果、与计划的偏差 | "实际怎么样了" |
| **[Post]** Follow-up | 发现的后续问题 | "还有什么要做" |

**更新时机:** 开始实施前写计划，实施后写回结果。

---

## 4. `execution/` — 实施记录 ("某天/某次做了什么")

> 每次重要实施一个文件。

**命名:** `YYYY-MM-DD_<topic>.md` 或 `<commit-hash>_<topic>.md`

| Section | 内容 | 用途 |
|---------|------|------|
| Date & Ref | 日期、关联的 design/plan/commit | "什么时候做的" |
| Changes | 具体改了什么文件/模块 | "动了哪些代码" |
| Issues | 遇到的问题和解决方法 | "踩了什么坑" |
| Verification | 测试/验证结果 | "测试通过了吗" |
| Notes | 备注、遗留问题 | "还有什么要注意的" |

**更新时机:** 完成重要实施后记录。

---

## 写作原则

1. **中文优先**：本项目文档使用中文，代码示例和技术术语保持英文
2. **简洁为上**：每个 section 只写必要内容，避免冗余
3. **可定位**：包含文件路径、行号、commit hash 等具体引用
4. **可验证**：包含验证步骤或预期结果
5. **及时更新**：代码变了就更新 architecture，不要让文档过时
